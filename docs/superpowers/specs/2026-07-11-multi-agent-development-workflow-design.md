# 多 Agent 开发流程设计

## 概述

本文档设计了 NapCat 项目的多 Agent 协作开发流程，通过职责分离和流程标准化，提高开发效率和代码质量。

## 设计目标

1. **职责分离** — 每个 Agent 专注自己的职责，不越权
2. **流程标准化** — 统一的开发、测试、修复流程
3. **上下文隔离** — 避免主 Agent 上下文压力过大
4. **问题明确后才能开发** — 不能凭假设改代码
5. **分支保护** — 任何改动都不能在 main 分支操作

## Agent 角色定义

### 1. 主 Agent（协调者）

**职责：**
- 接收用户需求/bug 报告
- 协调和委派任务给其他 Agent
- 创建分支/worktree
- 管理修复循环（最多3次）
- 用户确认后合并和推送代码

**权限：**
- 全部工具权限
- 但**不负责**任何分析和定位工作

**核心原则：**
- 只负责协调和委派，不经手分析工作
- 不能拿到需求就动手，必须先通过需求分析 Agent 理解清楚
- 遵守 branch-workflow 规则

### 2. 需求分析 Agent (requirement-analyzer)

**职责：**
- 接收用户需求，进行拆分和理解
- 不清楚的地方打回给用户
- 输出整理后的需求文档
- Bug 修复时：结合代码和日志定位问题
- 测试失败时：分析失败原因，指出可能的问题位置

**权限：**
- ✅ 读取代码文件（Read）
- ✅ 搜索代码（Grep, Glob）
- ✅ 读取日志文件（Read）
- ❌ 不能运行任何命令
- ❌ 不能修改任何文件
- ❌ 不能提交代码

**工具声明：**
```yaml
tools:
  - Read
  - Grep
  - Glob
```

### 3. 开发 Agent (developer)

**职责：**
- 根据需求进行代码开发
- 根据问题描述进行 bug 修复
- 在主 Agent 创建的分支上工作
- 遵守开发规范，遵循开闭原则
- 完成后提交代码（但不合并和 push）

**权限：**
- ✅ 读取代码文件（Read）
- ✅ 修改代码文件（Write, Edit）
- ✅ 运行命令（Bash）
- ✅ 搜索代码（Grep, Glob）
- ✅ 提交代码（git commit）
- ❌ 不能合并分支
- ❌ 不能推送到远程

**工具声明：**
```yaml
tools:
  - Read
  - Write
  - Edit
  - Bash
  - Grep
  - Glob
```

### 4. 测试 Agent (post-dev-tester)

**职责：**
- 运行测试脚本验证功能
- 查看日志获取执行结果
- 生成结构化测试报告

**权限：**
- ✅ 读取代码文件（Read）
- ✅ 运行测试脚本（Bash，仅限 scripts/ 目录）
- ✅ 读取日志文件（Read, Bash）
- ✅ 搜索代码（Grep, Glob）
- ❌ 不能修改任何文件
- ❌ 不能运行 scripts/ 以外的脚本
- ❌ 不能提交代码

**工具声明：**
```yaml
tools:
  - Read
  - Bash
  - Grep
  - Glob
```

**Bash 使用限制：**
- 只能执行 `scripts/` 目录下的脚本
- 禁止执行其他任何命令

### 5. 日志 Agent (log-reader)

**职责：**
- 根据查询条件读取和分析日志
- 提供结构化的日志总结

**权限：**
- ✅ 读取日志文件（Read, Bash）
- ✅ 搜索日志（Grep, Glob）
- ❌ 不能读取代码文件
- ❌ 不能修改任何文件
- ❌ 不能运行脚本

**工具声明：**
```yaml
tools:
  - Read
  - Bash
  - Grep
  - Glob
```

## 流程设计

### 流程一：新功能开发

```
用户需求
    ↓
[主Agent] 启动需求分析 Agent
    ↓
[需求分析Agent] 理解需求，不清楚的地方打回给用户
    ↓
[主Agent] 收到整理后的需求
    ↓
[主Agent] 创建分支
    ↓
[主Agent] 启动开发 Agent（注入上下文）
    ↓
[开发Agent] 开发并提交代码
    ↓
[主Agent] 启动测试 Agent（注入测试内容和预期结果）
    ↓
[测试Agent] 生成测试报告
    ↓
[主Agent] 判断测试结果
    ├─ 通过 → 交由用户体验和确认 → 用户确认后合并推送
    └─ 失败 → 转入修复失败流程
```

### 流程二：Bug 修复

```
用户报告 Bug
    ↓
[主Agent] 启动需求分析 Agent 初步分析问题
    ↓
[需求分析Agent] 分析问题，确定需要查看日志
    ↓
[主Agent] 委派日志 Agent 查看相关日志
    ↓
[日志Agent] 返回日志分析报告
    ↓
[主Agent] 把日志结果提交给需求分析 Agent
    ↓
[需求分析Agent] 结合代码和日志定位问题
    ├─ 日志足够 → 明确问题描述，返回给主 Agent
    └─ 日志不足 → 需求分析 Agent 自行查询日志补充信息
                    ↓
              需求分析 Agent 明确问题描述，返回给主 Agent
    ↓
[主Agent] 收到明确的问题描述
    ↓
[主Agent] 创建分支
    ↓
[主Agent] 启动开发 Agent（注入问题描述和上下文）
    ↓
[开发Agent] 修复并提交代码
    ↓
[主Agent] 启动测试 Agent（注入测试内容和预期结果）
    ↓
[测试Agent] 生成测试报告
    ↓
[主Agent] 判断测试结果
    ├─ 通过 → 交由用户体验和确认 → 用户确认后合并推送
    └─ 失败 → 转入修复失败流程
```

### 流程三：测试失败后的修复循环

```
测试失败
    ↓
[主Agent] 把测试报告提交给需求分析 Agent
    ↓
[需求分析Agent] 分析失败原因，指出可能的问题位置
    ↓
[主Agent] 把分析结果提交给开发 Agent 修复
    ↓
[开发Agent] 修复并提交代码
    ↓
[主Agent] 启动测试 Agent 再次测试
    ↓
    ├─ 通过 → 交由用户体验和确认
    └─ 失败 → 重复上述流程，最多3次
              仍有问题 → 主 Agent 告知用户问题并结束
```

## 上下文注入策略

### 开发 Agent 注入内容

- 整理后的需求文档
- 相关代码文件路径和关键代码片段
- 项目架构和技术栈信息
- 开发规范和约束（开闭原则、分支规则等）

### 测试 Agent 注入内容

- 开发内容摘要（改了什么、为什么改）
- 应该测试到的场景列表
- 预期执行结果
- 相关代码变更的 diff

### 问题修复时注入内容

- 明确的问题描述
- 问题定位分析（来自需求分析 Agent）
- 相关日志信息（来自日志 Agent）
- 相关代码文件路径

## 核心约束

### 1. 主 Agent 约束

- **不能经手分析工作** — 只负责协调和委派
- **不能拿到需求就动手** — 必须先通过需求分析 Agent 理解清楚
- **遵守 branch-workflow 规则** — 任何改动都不能在 main 分支操作

### 2. 需求分析 Agent 约束

- **只能读取和搜索** — 不能运行任何命令，不能修改任何文件
- **问题必须明确** — 不能模糊描述，必须指出具体的问题位置
- **可以自行查询日志** — 如果主 Agent 提供的日志不足，可以通过 Read/Grep/Glob 工具自行查询日志文件

### 3. 开发 Agent 约束

- **问题明确后才能开发** — 不能凭假设改代码
- **遵守开发规范** — 遵循开闭原则
- **不能合并和 push** — 只能提交代码，合并和推送由主 Agent 负责

### 4. 测试 Agent 约束

- **只能运行 scripts/ 目录下的脚本** — 禁止执行其他任何命令
- **不能修改任何文件** — 只读权限
- **生成结构化报告** — 必须输出测试结果和结论

### 5. 日志 Agent 约束

- **只能读取日志** — 不能读取代码文件，不能修改任何文件
- **按需查询** — 根据时间范围、用户ID、关键词等条件过滤日志
- **结构化输出** — 提供清晰的总结
